# MCP 2026 Alignment: Stateless Core, Tasks Extension, and an MCP App Surface

## Status

Created on 2026-07-05 from a market and product research pass. Completed on
2026-07-06: the gateway negotiates the 2026-07-28 RC revision alongside
`2025-06-18`, header routing (`Mcp-Method`/`Mcp-Name`) resolves through pure
gateway logic, read tools carry `ttlMs`/`cacheScope` cache metadata,
`ai_suggest_decision_log` runs through the SQLite-backed Tasks extension
(`tasks/get`/`tasks/cancel`, fail-closed on token revocation), and the MCP
App template renders the page outline, pending proposals, and the agent
journal tail as a self-contained HTML view (`cascadery://pages/{id}/app`).

Explicit future work, not hidden gaps:

- Final-release drift: re-verify header names, cache-metadata shape, and the
  Tasks/Apps extension wire format against the final 2026-07-28 spec once
  the RC validation window closes (open question held on purpose).
- The App's accept/reject buttons post review intents to the host
  (`cascadery:proposal-review` postMessage); hosts complete the review
  through the existing MCP tools under the caller's token scope. A
  server-side proposal inbox (so accepts round-trip without host mediation)
  is future work and must preserve the review-first AI posture.
- Dropping `2025-06-18` support: revisit after final-release adoption is
  visible.

Extends the completed remote MCP hardening spec
(completed/2026-07-02-remote-mcp-hardening.md). The MCP 2026-07-28 revision
is a release candidate with a validation window through July 28; implement
against the RC and re-verify details at final release.

## Goal

The MCP gateway pins `protocolVersion: '2025-06-18'`
(`src/mcpGateway.ts:582`). The 2026-07-28 revision is the largest protocol
change to date: a stateless core (no `initialize` handshake, no session ids,
new routing headers, response cache metadata), Tasks as an official
extension for long-running work, MCP Apps as an official extension for
server-rendered UI inside hosts, and hardened OAuth alignment. Agent authors
are Cascadery's growth channel; the gateway staying current is not
maintenance, it is distribution. This spec brings the gateway to the new
revision and ships one high-leverage MCP App: the page outline and proposal
review rendered inside the agent host.

## Current State

- The gateway (`src/mcpGateway.ts`, served by `app/api/mcp/route.ts`) is
  HTTP JSON-RPC and already effectively stateless per request: page-scoped
  bearer tokens (`src/server/mcpTokens.ts`) carry identity and scopes, and
  no session store exists. The remaining statefulness is protocol-shape:
  the `initialize` response advertising `2025-06-18`.
- Scopes (`page:read`, `page:search`, `page:suggest`, `page:write`) with
  per-scope rate limits (`src/server/rateLimit.ts`) and security logging
  (`src/server/securityLog.ts`) shipped with remote MCP hardening.
- Long-running work exists: `ai_suggest_decision_log` calls the GLM
  provider (`src/server/glmProvider.ts`, 20s default timeout) inline —
  exactly the shape the Tasks extension is designed for.
- The page outline helper (`getPageOutline`, keyboard/a11y spec) and the
  proposal review flow already produce the content an MCP App would render.
- Sampling, roots, and MCP logging are not used by the gateway — the three
  deprecations cost nothing.

## Scope

### Stateless core adoption

- Support the 2026-07-28 protocol revision: accept and answer the new
  version identifier, handle `Mcp-Method` and `Mcp-Name` request headers,
  and keep accepting `2025-06-18` `initialize` flows during a documented
  transition window (agent hosts will upgrade unevenly).
- Emit `ttlMs`/`cacheScope` on read-tool responses: short TTL for
  `get_page`/`get_area`/`search_areas` (the doc is live-collaborative),
  none for suggest/write tools. Cache metadata must never outlive a
  page-token revocation — pick TTLs below the revocation-check granularity.
- Version negotiation and header parsing live as pure logic in
  `src/mcpGateway.ts` with tests; the route stays thin.

### Tasks extension for long-running tools

- Adopt the Tasks extension lifecycle (`tools/call` returns a task handle;
  `tasks/get`/`tasks/cancel` drive it) for `ai_suggest_decision_log` and
  any future provider-backed tool. Task state persists in SQLite
  (`src/server/database.ts`) so any instance can answer `tasks/get`,
  honoring the stateless design.
- Fast tools keep returning results directly — Tasks only where real
  latency exists. Task records carry the token id; a revoked token's tasks
  fail closed on next poll.

### MCP App: page outline and proposal review in the host

- Declare one UI template on the gateway per the Apps extension: a
  self-contained HTML view (sandboxed iframe, no external requests —
  matching the app's existing no-CDN posture) rendering the page outline
  (reuse `getPageOutline` structure) and, when proposals are pending, the
  proposal list with accept/reject actions that call back through the
  existing proposal-review endpoints under the caller's token scope.
- Read-only for `page:read` tokens; accept/reject requires the same
  authority the web UI requires. The App is a *view* of existing state and
  existing actions — no new mutation paths, so the AI posture (visible,
  reviewable, audited) is preserved by construction.

### Authorization currency

- Apply the RC's authorization SEPs where the current user-minted-token
  model is concerned: issuer validation on any OAuth-compatible flows the
  hardening spec left as migration path, and document which SEPs only bind
  when a real authorization server arrives (identity spec follow-up).
- Confirm the deprecated features (roots, sampling, logging) are absent
  and note it in the gateway module docs.

## Non-Goals

- Building an OAuth authorization server (unchanged from the hardening
  spec: user-minted scoped tokens remain the model).
- MCP Apps beyond the single outline/proposal view (no canvas editor in an
  iframe).
- Registry listing and server discovery metadata — that belongs to the
  product-site spec's docs surface, though this spec unblocks it.
- Dropping `2025-06-18` support (transition window, revisit after final
  release adoption is visible).

## Acceptance Criteria

- A client speaking the 2026-07-28 RC revision can list and call every
  existing tool without an `initialize` round-trip; a `2025-06-18` client
  still works.
- Read-tool responses carry `ttlMs`/`cacheScope`; a revoked token's
  cached-window requests fail closed on next contact.
- `ai_suggest_decision_log` returns a task handle; `tasks/get` reports
  progress and final result across server restarts; `tasks/cancel` works;
  a `page:read` token cannot create the task.
- The declared MCP App template renders the live outline and pending
  proposals in a sandboxed iframe with zero external network requests;
  accepting a proposal from the App is attributed and audited identically
  to accepting in the web UI.
- All new denial paths are security-logged; `pnpm test`, `pnpm lint`, and
  `pnpm build` pass.

## Testing

  presence and absence per tool class.
- New `src/server/mcpTasks.test.ts`: task lifecycle create/get/cancel,

- `src/mcpRoute.test.ts`: RC-shaped HTTP requests end to end against the
  route handler.
- App template: unit-test the rendered HTML for zero external URLs and
  correct outline/proposal content given a fixture page state.
